Да. По открытым материалам можно довольно подробно объяснить защитную архитектуру и классы проверок, но без точных приватных порогов и инструкций по подстройке чита под них.

КАКИЕ АНТИЧИТЫ СТОЯТ НА ЭТИХ СЕРВЕРАХ

Надёжно подтвердить конкретный актуальный стек FunTime, HolyWorld, ReallyWorld и SpookyTime нельзя:

- официальные страницы серверов не публикуют список и конфигурацию защит;
- утверждения на форумах противоречат друг другу;
- крупные проекты обычно комбинируют публичный античит с собственными проверками, прокси-фильтрами и ручной модерацией;
- конфигурация может отличаться между режимами и меняться без объявления.

Например, в сообществе HolyWorld упоминают комбинации Grim, Matrix и Vulcan, а для SpookyTime — собственные combat-проверки вместе с отдельной защитой движения. Но это слухи, а не подтверждённая техническая документация. Профили с названиями серверов в чит-клиенте тоже ничего не доказывают.

Поэтому корректнее разбирать известные технологии: GrimAC, Matrix и кастомный серверный слой.

1. КАК РАБОТАЕТ GRIMAC

Grim — открытый античит, ориентированный прежде всего на детерминированную симуляцию клиента. Он поддерживает разные версии Minecraft, хранит для каждого игрока копию видимого мира, учитывает различия collision boxes, задержку доставки изменений блоков и состояние инвентаря.

Источник:
https://github.com/GrimAnticheat/Grim/blob/2.0/README.md

ОСНОВНАЯ ИДЕЯ

Вместо вопроса:

«Это движение кажется подозрительным?»

Grim старается ответить:

«Мог ли настоящий клиент Minecraft физически получить такое состояние?»

Упрощённо сервер имеет состояние игрока S_k и множество допустимых вводов U_k. Симулятор рассчитывает множество возможных следующих состояний:

S_(k+1) = F(S_k, U_k, world, version)

Затем полученный от клиента результат P_(k+1) сравнивается с допустимым множеством:

e_k = dist(P_(k+1), S_(k+1))

Если ошибка постоянно превышает допустимую погрешность, проверка повышает violation level.

ЧТО GRIM РЕКОНСТРУИРУЕТ

- скорость и позицию игрока;
- нахождение на земле;
- столкновения с блоками;
- воду, лестницы, паутину, лёд и другие поверхности;
- knockback;
- эффекты зелий;
- использование предметов;
- транспорт;
- sprint, sneak, jump;
- различия физических правил между версиями клиента;
- изменения мира, уже дошедшие до конкретного игрока.

Из-за per-player world replica античит может проверять состояние, которое клиент действительно должен был видеть, а не только текущий мир на сервере. Это уменьшает ложные срабатывания при задержке.

Источник:
https://github.com/GrimAnticheat/Grim/blob/2.0/README.md

ТИПЫ ПРОВЕРОК GRIM

В публичном списке указаны:

- Movement;
- Reach;
- NoFall;
- Timer;
- AntiKnockback;
- NoSlow;
- Scaffold и размещение блоков;
- BadPackets;
- crash checks.

Источник:
https://github.com/GrimAnticheat/Grim/wiki/Checks

Архитектурно проверки получают разные потоки событий: входящие и исходящие пакеты, position updates, rotation updates, действия с блоками и окончание предсказания движения.

Источник:
https://github.com/GrimAnticheat/Grim/blob/2.0/common/src/main/java/ac/grim/grimac/manager/CheckManager.java

СИЛЬНАЯ СТОРОНА GRIM

Сильнее всего Grim там, где нарушение можно доказать математически:

- невозможное движение;
- превышенная дистанция;
- неверный порядок пакетов;
- невозможная комбинация действий;
- несоответствие knockback;
- слишком быстрое внутреннее время клиента.

Сложнее строго доказать только по одному событию, что плавное наведение было выполнено человеком или автоматикой. Для этого серверы обычно добавляют эвристические или кастомные combat-проверки. В README Grim отдельно говорится о дополнительных heuristic checks в премиальных вариантах.

Источник:
https://github.com/GrimAnticheat/Grim/blob/2.0/README.md

2. КАК РАБОТАЕТ MATRIX

Matrix — преимущественно закрытая и конфигурируемая система, поэтому её точные современные формулы публично не раскрываются. В официальной документации проверки разделяются по назначению, включая KillAura, движение и другие категории.

Источник:
https://matrix.rip/docs/getting-started/concepts

Для каждой проверки администратор может:

- включать и выключать check/subcheck;
- менять схему наказаний;
- настраивать пороги;
- изменять внутренние параметры проверки.

Источник:
https://matrix.rip/docs/configuration/checks

В описании продукта отдельно перечислены combat-категории KillAura, AimBot, Reach, HitBox, MultiAura и AutoClicker.

Источник:
https://builtbybit.com/resources/matrix-anticheat.13999

ПРЕДПОЛАГАЕМАЯ ОБЩАЯ АРХИТЕКТУРА MATRIX

Без доступа к приватной версии можно уверенно говорить только о типовой схеме:

1. Перехват пакетов игрока.
2. Нормализация событий по tick.
3. Проверка геометрии атаки.
4. Проверка последовательности действий.
5. Расчёт rotation/click/movement-признаков.
6. Накопление violation level.
7. Отмена действия, оповещение персонала, kick или ban.

В отличие от чистой физической симуляции, combat-часть может использовать больше эвристик: отдельное событие не обязательно считается доказательством, но серия похожих аномалий повышает общий score.

3. КАК СЕРВЕР «ПАЛИТ» KILLAURA

A. ГЕОМЕТРИЯ АТАКИ

Сервер восстанавливает:

- положение глаз атакующего;
- направление взгляда;
- bounding box цели;
- допустимую дистанцию;
- препятствия между игроками.

Луч взгляда можно представить как:

r(t) = o + t × d

где:

- o — серверное положение глаз;
- d — направление из yaw/pitch;
- t — расстояние вдоль луча.

Затем проверяется пересечение с AABB цели. Атака подозрительна, если:

- луч не пересекает hitbox;
- ближайшее пересечение находится слишком далеко;
- перед целью находится блок;
- клиент атакует не ту сущность, на которую направлен серверный луч;
- атака произведена из состояния, которое сервер ещё не подтвердил.

Плавность камеры здесь не помогает: если серверная геометрия не сходится, движение может быть сколь угодно красивым.

B. LAG COMPENSATION

Простая проверка текущего hitbox давала бы много ошибок при высоком ping. Поэтому защита хранит историю:

tick → player position → target position → hitbox → world state

При атаке выбирается исторический snapshot, соответствующий моменту, который клиент мог видеть. Затем raycast выполняется против восстановленного hitbox.

Защита учитывает не только ping, но и:

- задержку обработки;
- порядок транзакций;
- телепорты;
- изменения блоков;
- смену измерения;
- version translation;
- потерю или объединение пакетов.

C. ПОРЯДОК ПАКЕТОВ

Даже если финальный угол выглядит корректно, последовательность пакетов может быть невозможной.

Анализируются, например:

- rotation и attack в одном simulation tick;
- несколько несовместимых действий подряд;
- attack до подтверждения нужного состояния;
- дублирующиеся или лишние пакеты;
- действия во время inventory/use-item состояния;
- противоречие между sprint, movement и attack;
- несколько атак по разным целям в недопустимой последовательности.

Grim прямо разделяет packet, position, rotation и prediction listeners, а также содержит семейства BadPackets, PacketOrder и MultiActions.

Источник:
https://github.com/GrimAnticheat/Grim/blob/2.0/common/src/main/java/ac/grim/grimac/manager/CheckManager.java

D. АНАЛИЗ РОТАЦИЙ

Сервер видит не движение мыши, а последовательность сетевых yaw/pitch:

Delta yaw_k = yaw_k - yaw_(k-1)

v_k = Delta yaw_k / Delta t

a_k = (v_k - v_(k-1)) / Delta t

j_k = (a_k - a_(k-1)) / Delta t

Из неё могут извлекаться:

- угловая скорость;
- ускорение и jerk;
- смены знака;
- остановки непосредственно на цели;
- ошибка относительно hitbox до и после атаки;
- повторяемость траектории;
- связь движения цели с движением камеры;
- переключения между целями;
- распределение yaw/pitch;
- соответствие сетке чувствительности;
- длительность удержания взгляда.

Важно: сама по себе высокая скорость или идеальная кратность GCD не доказывает использование чита. Надёжная защита объединяет несколько признаков и анализирует их на длинном окне.

E. КОРРЕЛЯЦИЯ С ЦЕЛЬЮ

Для каждого tick можно вычислить идеальный угол на цель theta*_k и фактический угол игрока theta_k. Тогда ошибка:

e_k = wrap(theta*_k - theta_k)

Автоматизация может проявляться не просто маленькой ошибкой, а подозрительной связью между:

- изменением положения цели;
- изменением угла игрока;
- моментом атаки;
- выбором конкретной точки hitbox.

Человек тоже хорошо наводится, поэтому одна точная атака ничего не означает. Значение имеет повторяемая статистика на большом количестве ситуаций.

F. ТАЙМИНГИ И AUTOCLICKER

Сервер рассматривает последовательность интервалов:

tau_i = t_i - t_(i-1)

Проверяются:

- дисперсия интервалов;
- повторяемость;
- привязка к одному tick phase;
- длинные серии одинакового CPS;
- bursts;
- атаки до восстановления cooldown;
- связь кликов с наведением и движением.

Простой случайный разброс также не обязательно выглядит естественно: случайность может иметь неправильное распределение или не зависеть от игрового контекста.

G. ПЕРЕКЛЮЧЕНИЕ ЦЕЛЕЙ И MULTIAURA

Признаки:

- слишком быстрая смена противоположных направлений;
- атаки разных сущностей практически одновременно;
- выбор цели вне текущего поля зрения;
- отсутствие естественного этапа наведения;
- атака цели, которая уже вышла из серверного snapshot;
- невозможные повороты головы и тела между атаками.

H. СОВМЕСТНАЯ ПРОВЕРКА ДВИЖЕНИЯ И БОЯ

Крупная защита не рассматривает KillAura изолированно. Она сопоставляет:

- движение;
- sprint reset;
- knockback;
- rotation;
- attack;
- использование предметов;
- положение цели.

Например, отдельно допустимая ротация и отдельно допустимое движение могут образовывать невозможную совместную последовательность.

4. КАК ИЗ АНОМАЛИИ ПОЛУЧАЕТСЯ НАКАЗАНИЕ

Хороший античит обычно не банит за одну слабую эвристику.

Типовая схема:

VL_(k+1) = max(0, lambda × VL_k + s_k)

где:

- s_k — тяжесть новой аномалии;
- lambda < 1 — постепенное затухание старых подозрений;
- VL — violation level.

Дальше возможны уровни реакции:

1. Только запись телеметрии.
2. Staff alert.
3. Отмена атаки.
4. Setback.
5. Kick.
6. Ban после достаточного количества независимых доказательств.

Для математически невозможного пакета реакция может быть быстрой. Для поведенческого анализа обычно требуется серия событий.

5. ПОЧЕМУ ОДНА «ХОРОШАЯ РОТАЦИЯ» НЕ ЯВЛЯЕТСЯ ОБХОДОМ

Контроллер второго порядка может устранить:

- резкие скачки;
- численные колебания;
- неправильное двойное GCD;
- часть синтетической регулярности.

Но он не исправляет автоматически:

- неправильную серверную дистанцию;
- атаку через препятствие;
- рассинхронизацию hitbox;
- неверный порядок пакетов;
- невозможные тайминги;
- MultiAura;
- несовместимость движения и атаки;
- повторяемое автоматическое переключение целей.

Сервер вообще не знает, что внутри клиента используется second-order controller. Он видит только итоговые пакеты и проверяет, образуют ли они допустимую последовательность.

ЕСЛИ СМОТРЕТЬ СО СТОРОНЫ РАЗРАБОТЧИКА ЗАЩИТЫ

Правильная защитная архитектура:

1. Считать клиент полностью недоверенным.
2. Хранить серверные snapshots игроков и мира.
3. Выполнять version-aware Ray–AABB проверку.
4. Обрабатывать пакеты через строгую state machine.
5. Разделять математически невозможные действия и статистические подозрения.
6. Использовать контекст ping, TPS, teleport, vehicle, velocity и смены мира.
7. Сначала запускать новые эвристики в shadow mode.
8. Сохранять replay/телеметрию для каждого серьёзного флага.
9. Объединять независимые сигналы, а не банить по одной синусоиде или GCD.
10. Постоянно измерять false-positive rate на легитимных игроках.

ИТОГ

Точный стек этих четырёх серверов публично не подтверждён, но почти наверняка речь идёт не об одной rotation-проверке. Крупная защита сочетает геометрию, симуляцию, packet state machine, временные проверки, статистику и ручную модерацию. Точные приватные пороги и способы их обхода я разбирать не буду, а defensive-часть — архитектуру собственного античита, систему snapshot/rewind и безопасную оценку сигналов — могу объяснять подробно.
