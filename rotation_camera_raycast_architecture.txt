Сразу обозначу границу: с учётом контекста KillAura я не могу помогать строить систему, специально имитирующую человека для обхода античита, или подгонять пакеты так, чтобы публичный сервер гарантированно принимал автоматические удары. Но могу подробно описать корректную модель камеры и серверную lag compensation для собственной игры, приватного стенда или тестирования античита.

1. Модель реалистичного движения камеры

Для непрерывного сопровождения движущейся цели лучше всего подходит не Bézier и не чистый шум, а комбинация:

1. система второго порядка — основное движение;
2. ограничения скорости, ускорения и рывка;
3. коррелированный шум небольшой амплитуды — только как визуальный эффект;
4. minimum-jerk траектория — для заранее известных переходов.

Ошибка угла

Для yaw обязательно выбирается кратчайшее направление:

e_y = wrap_[-180,180)(θ_y* − θ_y)

Для pitch:

e_p = θ_p* − θ_p

Нельзя просто вычитать yaw без wrap, иначе переход с 179° к −179° будет воспринят как поворот на −358°, хотя правильная ошибка равна 2°.

Физическая система массы и демпфирования

Удобная нормализованная форма:

θ̈ = ω_n²e − 2ζω_nθ̇

Где:

- θ — текущий угол;
- θ* — желаемый угол;
- e — угловая ошибка;
- ω_n — собственная частота, определяющая скорость реакции;
- ζ — коэффициент демпфирования;
- θ̇ — угловая скорость.

При ζ = 1 получается критически демпфированная система: она быстро приходит к цели без бесконечных колебаний. При ζ < 1 появляется overshoot, а при ζ > 1 движение становится слишком вязким.

Дискретная реализация через semi-implicit Euler:

a_k = ω_n²e_k − 2ζω_nv_k

v_(k+1) = clamp(v_k + a_kΔt, −v_max, v_max)

θ_(k+1) = θ_k + v_(k+1)Δt

Semi-implicit Euler предпочтительнее обычного Euler: сначала обновляется скорость, затем положение. Он устойчивее при плавающем времени кадра.

Дополнительно следует ограничить ускорение и jerk:

a_k ← clamp(a_k, −a_max, a_max)

a_k ← clamp(a_k, a_(k−1) − j_maxΔt, a_(k−1) + j_maxΔt)

Именно ограничение jerk устраняет резкие изменения ускорения, которые визуально воспринимаются как механические переключения.

Minimum-jerk вместо Bézier

Для заранее известного перехода между двумя ориентациями можно использовать квинтическую кривую:

s(u) = 10u³ − 15u⁴ + 6u⁵,    u = clamp(t/T, 0, 1)

θ(t) = θ₀ + wrap(θ₁ − θ₀)s(u)

У этой функции скорость и ускорение равны нулю на обоих концах. Поэтому она обычно выглядит естественнее обычного cubic Bézier.

Однако для постоянно движущейся цели minimum-jerk приходится всё время перепланировать. Если при каждом изменении цели начинать новую кривую с нулевой скоростью, возникнут микропауызы. Поэтому:

- для scripted camera transitions — minimum-jerk;
- для continuous tracking — система второго порядка;
- Bézier — преимущественно для художественно заданных движений камеры.

Какой шум использовать

Белый шум

Добавлять независимое случайное число непосредственно к углу плохо:

θ'_k = θ_k + σξ_k

Это создаёт высокочастотную дрожь и разрывы производной.

Perlin/Simplex

Perlin и Simplex дают плавный сигнал, но он остаётся процедурным и может обладать заметным спектром. Они хорошо подходят для:

- покачивания камеры;
- ветра;
- дыхания;
- cinematic effects.

Для физической модели управления они менее удобны, потому что не описывают скорость и ускорение.

Процесс Орнштейна—Уленбека

Для эстетического коррелированного шума лучше подходит mean-reverting процесс:

n_(k+1) = n_k e^(−Δt/τ) + σ√(1 − e^(−2Δt/τ)) ξ_k

Где ξ_k ~ N(0,1), а τ задаёт время корреляции.

Такой шум:

- непрерывнее белого;
- естественно возвращается к нулю;
- не имеет жёсткого периода, как синусоида;
- может добавляться к ускорению или к визуальной точке камеры.

Лучше добавлять его к угловому ускорению, а не к финальному углу:

a'_k = a_k + n_k

Для визуальной камеры можно смешать медленную составляющую и микродвижение:

n = n_slow + n_micro

Но шум не должен исправлять плохой контроллер. Сначала движение должно быть стабильным без шума.

2. Правильная цепочка обработки ориентации

В текущем проекте некоторые профили самостоятельно округляют результат по GCD, а затем RotationStorage снова применяет GCDUtil.getFixedRotation. Это и есть двойное квантование: два компонента последовательно изменяют одну и ту же величину.

Корректная цепочка для собственной игры должна выглядеть так:

Target snapshot
      ↓
Aim-point policy
      ↓
Desired orientation
      ↓
Motion controller
      ↓
Rate / acceleration / pitch constraints
      ↓
Input quantizer — ровно один раз
      ↓
Authoritative local rotation state
      ├──→ Renderer interpolation
      └──→ Network serialization

Этап 1: согласованный снимок цели

Все вычисления одного simulation tick должны использовать один и тот же снимок:

record TargetSnapshot(
    long tick,
    Vec3d position,
    Vec3d velocity,
    Box hitbox
) {}

Нельзя взять позицию из текущего кадра, hitbox из предыдущего сетевого обновления, а скорость — после следующего события. Это создаёт внутренний рассинхрон даже до отправки данных.

Этап 2: вычисление желаемой ориентации

Для точки P_t и позиции глаз P_e:

d = P_t − P_e = (d_x, d_y, d_z)

yaw = atan2(−d_x, d_z)

pitch = atan2(−d_y, √(d_x² + d_z²))

После преобразования в градусы pitch ограничивается допустимым диапазоном.

Этот этап должен вычислять только идеальное геометрическое направление. Здесь не должно быть GCD, плавности или сетевой логики.

Этап 3: контроллер движения

Контроллер принимает текущие angle/velocity и желаемую ориентацию:

interface OrientationController {
    ControllerOutput step(
        OrientationState current,
        Orientation desired,
        double dt
    );
}

Результат лучше представлять как угловое приращение и новую скорость:

record ControllerOutput(
    Vec2f angularDelta,
    Vec2f angularVelocity
) {}

Контроллер не должен изменять объект игрока напрямую.

Этап 4: ограничения

Отдельный компонент применяет:

- ограничение pitch;
- максимальную скорость;
- максимальное ускорение;
- максимальный jerk;
- при необходимости ограничения конкретного режима камеры.

Это позволяет тестировать ограничения независимо от геометрии цели.

Этап 5: единственное квантование

Квантуется не абсолютный угол, а рассчитанное приращение:

q = round(Δθ/g)g

Где g — шаг ввода.

Чтобы маленькие приращения не терялись, используется остаточный аккумулятор:

x_k = Δθ_k + r_k

q_k = round(x_k/g)g

r_(k+1) = x_k − q_k

Например, если несколько последовательных приращений меньше одного шага, их остатки накапливаются, а не исчезают. Это аналог error diffusion.

Но если движок уже обрабатывает реальные mouse deltas и сам применяет sensitivity transform, лучше вообще не рассчитывать GCD вручную — передавать дельту в официальный input layer.

Этап 6: единый источник состояния

После квантования ориентация фиксируется один раз:

rotationState.commit(quantizedDelta, simulationTick);

Затем:

- renderer интерполирует предыдущий и текущий committed state;
- сеть сериализует текущий committed state;
- никакой дополнительной математики на сетевом этапе нет.

Сетевой код не должен повторно:

- сглаживать;
- округлять;
- ограничивать скорость;
- выбирать точку;
- изменять yaw/pitch.

Иначе визуальная, simulation- и network-ориентации начинают расходиться.

Разделение render tick и simulation tick

Контроллер лучше обновлять на фиксированном simulation tick:

void simulationTick(double fixedDt) {
    TargetSnapshot snapshot = targetProvider.snapshot();

    Orientation desired =
        orientationSolver.lookAt(cameraOrigin(), snapshot.point());

    ControllerOutput raw =
        controller.step(rotationState.current(), desired, fixedDt);

    Vec2f constrained =
        constraints.apply(raw.angularDelta(), fixedDt);

    Vec2f quantized =
        quantizer.apply(constrained);

    rotationState.commit(quantized);
    networkPublisher.publish(rotationState.snapshot());
}

Render loop только интерполирует:

θ_render = lerpAngle(θ_previous, θ_current, α)

Он не должен менять сетевое состояние.

3. Raycast, задержка и интерполяция

Главное ограничение

Клиент не может сделать так, чтобы сервер всегда принимал попадание. Сервер может использовать:

- другую позицию игрока;
- другую ориентацию;
- другой hitbox цели;
- собственную дистанцию;
- cooldown;
- line-of-sight;
- правила конкретного оружия;
- собственный порядок пакетов.

Правильное решение для своей игры — не пытаться угадывать сервер на клиенте, а реализовать server-side rewind.

История трансформаций на сервере

Сервер хранит кольцевой буфер:

record TransformSnapshot(
    long serverTick,
    double serverTime,
    Vec3d position,
    Box hitbox,
    float yaw,
    float pitch,
    Pose pose
) {}

При получении атаки сервер выбирает исторический момент, соответствующий видимому клиенту состоянию. Предпочтительно передавать не произвольное клиентское время, а номер последнего подтверждённого серверного snapshot и input sequence.

Клиентское значение используется только как подсказка; сервер ограничивает rewind допустимым окном.

Интерполяция исторического состояния

Если искомое время находится между t₀ и t₁:

α = clamp((t_s − t₀)/(t₁ − t₀), 0, 1)

P(t_s) = P₀ + (P₁ − P₀)α

Yaw интерполируется по кратчайшему пути:

yaw(t_s) = yaw₀ + wrap(yaw₁ − yaw₀)α

Для hitbox лучше восстановить соответствующие:

- позицию;
- pose;
- размеры;
- состояние приседания/полёта.

Просто сдвинуть текущий AABB в старую позицию недостаточно, если поза за это время изменилась.

Ray–AABB

Луч:

R(t) = O + tD,    0 ≤ t ≤ L

Где:

- O — серверная позиция глаз атакующего;
- D — нормализованное сервером направление;
- L — допустимая дистанция.

Для каждой оси применяется slab test:

t_(1i) = (B_min,i − O_i)/D_i

t_(2i) = (B_max,i − O_i)/D_i

t_enter = max_i(min(t_(1i), t_(2i)))

t_exit = min_i(max(t_(1i), t_(2i)))

Попадание существует, если:

t_enter ≤ t_exit,
t_exit ≥ 0,
t_enter ≤ L

Отдельно необходимо проверить блоки: расстояние до первого пересечения с collision shape блока должно быть больше расстояния до hitbox цели.

Серверная последовательность проверки

Для собственной игры обработчик удара должен:

1. проверить input sequence и исключить повтор пакета;
2. восстановить историческую позицию атакующего;
3. восстановить исторический hitbox цели;
4. построить луч из серверной позиции глаз;
5. проверить пересечение с hitbox;
6. проверить блоки и line-of-sight;
7. проверить reach;
8. проверить cooldown и оружие;
9. проверить, что цель была жива и доступна в выбранный tick;
10. только после этого применить урон.

Направление, origin, hitbox или дистанцию, присланные клиентом, нельзя считать доверенными.

Почему клиентская экстраполяция не гарантирует удар

Прогноз:

P_predicted = P + VΔt

работает только при приблизительно постоянной скорости. Он ломается при:

- изменении направления;
- столкновении;
- прыжке;
- knockback;
- изменении pose;
- packet jitter;
- серверной коррекции позиции.

Поэтому клиентская prediction годится для визуального crosshair, но не должна определять серверную валидность. Серверный rewind существенно надёжнее.

Рекомендуемые классы

TargetProvider
└── создаёт согласованный TargetSnapshot

AimPointPolicy
└── выбирает точку в пределах модели/объекта

OrientationSolver
└── преобразует точку в идеальные yaw/pitch

SecondOrderOrientationController
└── хранит velocity и acceleration

AngularConstraints
└── ограничивает rate, acceleration, jerk и pitch

InputQuantizer
└── единственное место квантования, хранит residual

RotationState
└── единственный authoritative local state

RotationPipeline
└── управляет порядком стадий

RotationRenderer
└── интерполирует committed snapshots

NetworkPosePublisher
└── только сериализует committed state

TransformHistory
└── серверный буфер исторических состояний

LagCompensator
└── выбирает ограниченный rewind tick

RaycastValidator
└── проверяет entity hitbox и блоки

AttackValidator
└── reach, cooldown, weapon, sequence, game rules

Полезно также возвращать с тестового сервера диагностический код отклонения:

MISS_ENTITY
BLOCKED_BY_WORLD
OUT_OF_REACH
STALE_INPUT
COOLDOWN
INVALID_ORIGIN
INVALID_ORIENTATION

Тогда можно сравнивать client ray и server ray без попыток заставить сервер принимать невалидные попадания.
